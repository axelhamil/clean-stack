## consents

1. Responsibility: records and withdraws cookie consent as an append-only ledger (one `consent_record` row per decision, grant TTL or refusal TTL), keyed by an anonymous subject cookie and optionally a user id. Reconciles guest records to the account at login and emits one outbox event per change. Retention sweep of guest rows lives in the host (`apps/api/src/shared/internal-routes/sweep-consents.route.ts`).
2. Business or technical, domain justified? Business (compliance evidence) but thin. DDD domain is not justified. Invariants found: "necessary" is always added (`modules/consents/src/application/services/consent.service.ts:48-50`), TTL differs for grant vs refusal (lines 61, 96), latest active record wins (`drizzle-consent.store.ts:39-53`), reconcile only emits when rows changed owner (service lines 134). All are one-line rules over an append-only log with no state transition on an existing record (a withdraw inserts a new row instead of mutating, service lines 84-107). A `Consent` entity would carry no invariant that a use case with a pure helper cannot hold. Verdict: Clean Architecture, no `domain/`.
3. Tree of `modules/consents/src` (11 files): `consents.module.ts`; `application/config/` 1 (`consent-settings.ts`); `application/dto/` 1; `application/ports/` 1; `application/services/` 1; `infrastructure/http/` 1; `infrastructure/repositories/` 1; `__TESTS__/` 3. Owned schema `modules/consents/schemas/consent.ts` (1 table, `consent_record`). No `domain/`, `mappers/`, `event-handlers/`.
4. Service vs use case: `ConsentService` (`application/services/consent.service.ts`, 185 lines) is use case orchestration, not a technical service. Public methods: `record` (45), `withdraw` (84), `getActive` (109), `reconcile` (127) = 4 use cases (`record-consent`, `withdraw-consent`, `get-active-consent`, `reconcile-consent`). Private `append` (155) is the shared uow + insert + emit; it becomes a small shared helper or an application service `ConsentLedger`. Constants/IDs: `crypto.randomUUID()` called in the service (lines 54, 89).

## policies

1. Responsibility: records which version of each legal policy (terms, privacy, ...) a user accepted, as an append-only log, and answers whether the user is up to date against the current versions held in `@packages/policies`. Feeds the `requireCurrentPolicies` route guard and the auth hooks.
2. Business or technical, domain justified? Business (compliance) but the rule is a version comparison: `acceptedVersion === POLICY_VERSIONS[t]` (`modules/policies/src/application/services/policy-acceptance.service.ts:73`) and `stale = types not current` (85). Versioning is config (`@packages/policies` `POLICY_VERSIONS`, `POLICY_TYPES`), not an aggregate: there is no entity that evolves, acceptance rows are inserted and never mutated, and "latest wins" is an SQL ordering (`drizzle-policy-acceptance.store.ts:57-72`). The guide's own test applies (`includes()` / config lookup / `count(*)` = infra). A domain is not justified. Only invariant worth naming: accept defaults to the stale types when no types are sent (route lines 27-32) and an empty list is a no-op (service line 28).

## profile

2. Business or technical, domain justified? A thin preference module. Domain not justified: one enum-validated field, no invariant (`isLocale` guard at read, `drizzle-profile.store.ts:61`). It owns no table: it reads and writes `authSchema.user.locale` (kit table, allowed by contract 5). Note the module guide's own test "Not a module" (rule 3): removing it leaves a module file, one store and one route; it passes the module bar only because of the route and event. ## rgpd

1. Responsibility: account erasure (GDPR Art. 17) in two phases (request with grace period, then a sweep-driven irreversible wipe in one transaction) and personal data export (Art. 20, JSON uploaded and presigned). Orchestrates ports served by admin, api-token, storage, email and TOTP. Documented in `modules/rgpd/CLAUDE.md`.
2. Business or technical, domain justified? Business, and the only one of the four with real ordering and survival rules. Honest assessment: partly justified. Invariants (file paths):
   - Two-phase state machine on the user: `none -> pending(until) -> cancelled | wiped`; wipe only when `pendingDeletionUntil <= now` (`modules/rgpd/src/application/services/rgpd.service.ts:268`), cancel refused after wipe or without a pending request (207-218), request is idempotent when already pending (115-118). Pure rule, no aggregate holds it today: the state lives in 3 columns of the kit `user` row (`deletedAt`, `pendingDeletionUntil`, `lastExportRequestedAt`, port `rgpd.port.ts:93-101`).
   - Request refusal rules: sole owner of non-personal org with other members (service 120-131, SQL in `drizzle-rgpd.repository.ts:47-115`), last staff manager decided inside the unit after the lock (service 391-411), TOTP if 2FA else password (133-155).
   - Wipe ordering and survival: user row survives anonymised (`drizzle-rgpd.repository.ts:310-323`), then staff data, sessions, accounts, two-factor, passkeys, memberships, invitations, tokens, organisations (339-399); all in one transaction, rollback if the confirmation email cannot be enqueued (service 339-357); idempotent via `WHERE deleted_at IS NULL` (322, 325-337); storage purged after commit by `<userId>/` prefix, failure logged (service 384, 622-642); sweep deadline checked between wipes (service 467-481).
   - Export rate limit `exportRateLimitHours` (service 530-539).
   Judgement: a small `deletion` domain (a `DeletionRequest` state machine VO plus a domain service `ErasureEligibility` for the grace and rate-limit arithmetic) is defensible and testable without a database, but it would not own the wipe: the wipe touches kit tables (`user`, `session`, `account`, `member`, `organization`, `invitation`, `twoFactor`, `passkey`) and 3 other modules' ports in one transaction, so it stays an infra port (`IAccountEraser`) sequenced by a use case. An aggregate with `_props` over `UserDeletionState` would be anemic (every field is a nullable column). Recommendation: Clean Architecture first; add a minimal `domain/deletion/` (state VO + eligibility service, 2 to 3 files) only if the plan wants the state machine tested in isolation. Not required by the invariants as documented.
