# Email delivery (`packages/email`)

**Emails enqueued, never sent inline.** `IEmailService` (`QueuedEmailService`) writes to `email_message` through the ambient executor: inside a `uow.run()` the row joins the caller's TX (atomic), outside one it autocommits. `EmailDeliveryWorker` polls every 2 s, delivers via `resend.batch.send` (100 emails/request, 10 req/s ceiling, `batchValidation: "permissive"`).

- **Never call Resend directly from a request path.** Use `di.IEmailService.sendTemplate(...)` or `di.IEmailService.sendTemplateBatch(...)`.
- **Failure is best-effort**: logs at `warn`, never rolls back the caller.
- **`@packages/emails` is the template SSOT.** `TEMPLATE_IDS` in the worker is an override; empty string = render in-repo React Email template. New templates: add to both the package and the `EmailTemplates` port type.
- **Lease model**: the one every delivery worker runs, `packages/outbox/CLAUDE.md`. Here the claim is `IEmailQueue.claim({ limit, leaseSeconds })` with `EMAIL_LEASE_SECONDS`, the settles are `markSent` / `markFailed`, and on stop unstarted chunks are released (`attempts - 1`, due now). The kit reads no env: the container passes the sender, `RESEND_FROM` and every knob to `EmailDeliveryWorker`.
- **Retry via decorrelated jitter** (`@packages/outbox/jitter`, `failureSchedule`). A retryable failure keeps the row `pending`; on its 4th failed send it is `dead` and replayed every `EMAIL_DEAD_RETRY_HOURS`, only while younger than `EMAIL_DEAD_REPLAY_WINDOW_HOURS` (a stale reset or sign-in link is never sent late). A permanent rejection is `failed`, terminal, never claimed. `email.delivery.exhausted` is emitted once, on the first death or the permanent rejection, in the settle's unit of work. The sweep purges `failed` and `dead` together. The batch call aborts after `EMAIL_SEND_TIMEOUT_SECONDS` (retryable), the worker releases the chunks its remaining lease no longer covers, and a row that fails to render is settled `failed` alone without stopping the chunk.
- **A chunk is replayed identically, under the same key.** Rows without a `batch_key` are grouped by kind, template, dead or live, and `attempts`, so one chunk shares one fate. Before the send, the worker writes `batch_key` = sha256 of the sorted row ids on the whole chunk, in one update limited to the rows it still leases (`assignBatch`); if the write fails or the lease is gone, nothing is sent and the chunk is released. The claim pulls every due sibling of a claimed `batch_key` (dead siblings only inside the replay window) and returns, per batch, how many unsettled rows are still in the table (`unsettledInBatch`: `pending`, or `dead` inside the window). `groupRows` keeps a batch whole. A batch claimed with fewer rows than that count is released with a warning and never sent: its missing rows are locked or leased elsewhere. A batch that already has a `batch_key` keeps it, it is never recomputed. Rows `sent`, `failed`, purged or `dead` past the window are settled and never make a batch incomplete. A whole-chunk failure is settled in one update for the chunk, from its highest `attempts`. Why: a crash, a lost lease or a failed `markSent` after an accepted send still leaves the key on the rows, so the replay rebuilds the same request.
- **The `Idempotency-Key` is sha256 of `batch_key` plus a canonical fingerprint of the entries actually sent.** `batch_key` only identifies the group. Why: a deploy that changes `RESEND_FROM`, `TEMPLATE_IDS` or a template changes the payload, and the same key with a different payload is refused by Resend; a new key risks at worst one duplicate, never a loss. `resendBatchSender` maps every provider error to a neutral `kind` (`retryable`, `in_flight`, `conflict`, `rejected`); the worker only switches on it. `in_flight` (409 `concurrent_idempotent_requests`, the original is still processing) releases the chunk 60 s later without spending an attempt: it never turns dead nor announces. `conflict` (409 `invalid_idempotent_request`) settles the rows `failed` with an explicit `last_error` and is captured. `EMAIL_DEAD_REPLAY_WINDOW_HOURS` is capped at 24 at boot, the lifetime of a Resend key: a later replay could send twice.
- Proven by `check:email-lease` and `check:marksent`; re-run both after touching the queue or the worker.
