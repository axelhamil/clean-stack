## 🚧 What's left

The plumbing a SaaS boilerplate owes its cloner is shipped: auth + MFA, multi-tenant with a capability SSOT, RGPD Art. 17/20, cookie consent, policy versioning, billing + quota gating, security perimeter, admin + impersonation, API tokens, audit log, outbound webhooks, in-app notifications, durable email delivery, enterprise SSO (OIDC + SAML) + SCIM provisioning, a typed i18n rail (`en`/`fr`), event rail (81 events / 35 public / 46 internal), Railway reference deploy. Per-phase detail below, as-built record in [`docs/HISTORY.md`](docs/HISTORY.md).

What remains is short on purpose. **Everything not listed here was cut** — a boilerplate that carries a wishlist of twelve unbuilt phases reads as unfinished when it isn't.

| | What | Why it survived the cut |
|---|---|---|
| **Review pass** | Full manual review of the shipped surface — owned by @axelhamil, not a code task | The only thing standing between "feature-complete" and "clone-ready" |
| **E.1b** | Remaining i18n extraction (`admin`, `webhooks`, `sso`, `billing`, `organization`, the rest of `settings`, per-locale legal content) — ~249 strings over 69 files, plus legal prose that has no `fr` version at all | E.1a shipped the rail and typed the surface it covers; what is left is catalog work, not a design decision |
| **C.1** | S5b behavioural signals + S6 captcha hook | Deferred for calibration, not abandoned — needs real traffic |
| **D.6** | Instrumentation spans on the `/internal/sweep-*` rail — not the runner, not the six `purgeBatch` implementations, not `sweep_lock` | Deliberately deferred: instrumenting only the lease (repo rule #8) would produce an incoherent trace with the runner and the batches around it left dark |
| **H.1** | Back ↔ front surface parity audit — every backend capability reachable from the UI, or explicitly declared UI-less | Runs last on purpose: it audits the finished surface. A route with no consumer is either a missing screen or dead code, and the boilerplate can afford neither |

**Cross-cutting, at first consumer**: one-click unsubscribe (RFC 8058 — Gmail/Yahoo require it for bulk senders) and SPF + DKIM + DMARC `p=reject` (DNS, doc only).

**Cut and not coming back**: marketing site (E.2), status page + SLO dashboards (D.1), SOC2 checklist (D.4), OpenAPI docs (D.2), Capacitor shell (F.1), feature flags (F.2), GPC (A.7), NIS2 readiness, and the per-phase "deferred" micro-items. Each was either a per-clone decision, a third-party service to wire, or an ambition with no substrate to exercise it. Git history has the specs if one becomes real.

**Out of scope**: HIPAA tooling, real-time WebSocket bus, third-party app marketplace, A/B testing framework, IAB TCF v2.2.

## Accessibility gate — axe in CI — **Phase A.6** ✅ SHIPPED (Aug 2026)

**Why**: WCAG 2.1 AA is an EAA obligation since 28 June 2025, and `/legal/accessibility` already publishes a conformance claim the repo must be able to back. A11y regressions ship invisibly — no user files a bug, the fine arrives instead. This is the one gate kept from A.6; the Playwright legal-chain scenarios were cut in favour of a manual review pass.

**Shipped (Aug 2026).** `apps/app/a11y/` (Playwright + `@axe-core/playwright`) + `.github/workflows/ci.yml` — **the repo's first PR-triggered CI**, until now every gate ran only in the local pre-push hook. Job: postgres service → `bootstrap` → `db:push` → `db:seed` → API on `:3000` → `turbo run check:a11y` (builds, then audits the preview build on `:4173`). Runs in ~2 s of test time once the app is built. As-built in [`docs/HISTORY.md`](docs/HISTORY.md); how to run it locally in [`apps/app/a11y/README.md`](apps/app/a11y/README.md).

- [x] **`@axe-core/playwright`** over 4 public + 3 authenticated pages, **in both colour schemes** — zero `serious`/`critical` WCAG 2.1 A/AA violations blocks merge. Playwright enters as an axe driver, not as an E2E suite. Authenticated pages reached through a `storageState` setup project that signs in via the UI. Dark is a `test.use({ colorScheme })` loop over the same lists: `next-themes` defaults to `system`, so the emulated preference is enough — and it caught a violation light never shows.
- [x] **Landmark coverage** — exactly one `<main>` and one `<h1>` per page, asserted per page. `audit()` also asserts the **final URL**: a session or policy gate redirect renders a page that satisfies every other assertion, so without it the suite audits the redirect target and reports green.
- [x] **Keyboard + reduced-motion**: tab order across every `/sign-in` control, focus trap on the command palette (10 Tab presses + Escape), and `prefers-reduced-motion: reduce` skipping the theme view transition — observed through a `MutationObserver` on `theme-transitioning`, since the class is gone by the time the transition ends.
- [x] **Lighthouse dropped.** Its a11y category runs a subset of axe: a budget of 100 restates what a zero-violation axe run already proves, for ~2 min of CI and an extra flake source. Deliberate deviation from the original spec.
- [x] **Seven real defects found and fixed** — the point of the gate: (a) `FormTextField` wrapped `<FormControl>` around the reveal-button `<div>`, so the generated `id` landed on the div and **every password field in the app had no accessible label** (`label`, critical); (b) `AuthShell` rendered its title through `CardTitle` (a `<div>`), leaving `/sign-in` and `/sign-up` with **no `<h1>` at all** — `CardTitle` now takes `asChild`; (c) `--accent-foreground` on `--accent` measured 4.27:1 in light (active nav pill); (d) `--destructive` measured 3.85:1 as text on a card *and* behind white on a button, and the destructive `Alert` description compounded it with `/90` opacity down to 3.36:1 — opacity gone, token darkened to L 0.58; (e) the avatar `input[type=file]` was `sr-only` with no `aria-label`; (f) **dark only**: `--primary` measured 4.12:1 under white on every default button — L 0.6132 → 0.58; (g) **dark only**: the impersonation `Alert variant="banner"` measured 2.76:1, now `dark:bg-destructive/60`, the convention Button and Badge already used. **The three token changes shift the palette slightly** — intentional, WCAG-driven.
- [x] **Two clone-blocking bugs in `db:seed`, surfaced by needing a real account**: the default `dev@clean-stack.test` is rejected by the S5a disposable-email guard (`.test` is reserved, can never carry an MX record → read as throwaway) and the default password contained the email local part, which the NIST policy rejects. Both defaults changed (`dev@example.com`); the script now also records the **initial policy acceptance** the `/verify-email` hook would have recorded, since forcing `emailVerified` in SQL skips it — without it every sign-in lands on `/legal/accept`.
- [x] **One sign-in per run, by construction.** `/sign-in` is capped at 5 attempts/15 min per IP and the block is held in-process (`inMemoryBlockDuration`), so the setup signs in *with the keyboard* and the interaction spec asserts tab order without submitting. Two sign-ins per run would make three consecutive local runs lock the developer out.

**A note on measuring**: hand-computing oklch → sRGB ratios pointed at the wrong defect. Tailwind mixes opacity in oklab, so `bg-destructive/60` is far darker than a linear-sRGB blend predicts — the calculation condemned every destructive button in dark (fine in reality) and missed `--primary` (actually broken). Every value in this phase is an axe measurement of the rendered page; the arithmetic only proposed candidates.

**Not covered**: Lighthouse budgets for perf/SEO. Screen-reader behaviour (no automated tool covers it). Surfaces that require a specific session to render — the impersonation banner was measured by injecting it into a page, not by a test, so it has no regression guard.

## Security perimeter — rate-limit + CSP + CSRF — **Phase C.1**

**Shipped (Jun–Jul 2026, S1–S5a).** Unified `rate-limiter-flexible` middleware fail-closed on auth (OWASP A10:2025, IETF `RateLimit` headers, trusted-proxy CIDR, memory/Postgres dedicated-pool stores; BetterAuth built-in `rateLimit` disabled for single source of truth). Strict CSP via **Caddy nonce** (`{http.request.uuid}` placeholder + `html.cspNonce` in Vite — not a Hono middleware; SPA is Caddy-served; `/csp-report` public, IP-rate-limited, CORP-hardened). **Deployment reminders**: `RATE_LIMIT_STORE=memory` is per-replica — switch to `postgres` before horizontal scaling; `TRUSTED_PROXIES` must be set behind a load-balancer (collective lockout risk if unset).

**Remaining — S5b + S6**, both deferred until real traffic exists to calibrate the false-positive rate (VPN and carrier-NAT wreck geo heuristics; device fingerprints are bypassable):

- [ ] **Behavioural signals (S5b)** — impossible-travel on sign-in (`session.ipAddress` + `userAgent` are already stored), accounts-per-visitor cap, env-driven country/ASN deny-list. Each emits a `security.*` event.

## API tokens / Personal Access Tokens — **Phase C.4** ✅ SHIPPED (Aug 2026)

**Why**: any B2B SaaS exposes its API to customer systems. PATs are the standard primitive (OAuth-app flow comes later if needed). Without them, customers integrate via screen-scraping or session-cookie-stealing — both bad.

**Relation to BetterAuth** (default-to-the-lib): BetterAuth ships an OSS `apiKey` plugin (`@better-auth/api-key@1.6.26`, self-hostable). **Evaluated 2026-08-06 → hand-roll** (`modules/api-token/`). It covers table + SHA-256 + expiry + CRUD, but: (a) **no lifecycle hooks** — rule #6 (event in the same TX) forces wrapping every endpoint anyway; (b) `referenceId` is user **XOR** org, never both — no "org token, created by member X" without custom columns; (c) its DB rate-limit does one `UPDATE` per request and duplicates `rate-limiter-flexible` (C.1/S4.1); (d) permissions are stored but never enforced. Once wrapped, what remains is a table with 8 dead columns against a `ScopedRepository` that natively honours instrumentation (rule #8) and the outbox. Steal its permission format and column list, not its runtime.

**Design decisions (2026-08-06)** — org-scoped · HMAC-SHA256 + server pepper · CRC32 checksum.

- [x] DB schema `api_token(id, userId FK, organizationId FK nullable, name, tokenHmac unique indexed, pepperVersion, tokenStart, scopes jsonb, lastUsedAt, expiresAt, createdAt, revokedAt nullable, revokedReason nullable)`. `userId` is both creator and owner — no separate `createdByUserId`, cascade revocation makes them the same person. Token shown ONCE at creation. **`ScopedRepository<ApiToken, RepoScope>`** (first consumer in the codebase — the interface ships in `ddd-kit` but nothing implements it yet) — wrong-owner returns `Option.none()` / `NOT_FOUND`, never 403.
- [x] Storage: `HMAC-SHA256(pepper, token)` in a unique-indexed column, **not** sha256 + per-row salt — a per-row salt destroys the O(1) lookup (forces a table scan) and buys nothing against a 256-bit secret (rainbow tables are inconceivable). The pepper (`API_TOKEN_PEPPER`, env/Vault, required in prod) is the real gain: a DB dump alone yields no usable token — the D.4 SOC2 argument. `pepperVersion` column allows rotation. Transparent rehash via `API_TOKEN_PEPPER_PREVIOUS` on next use — zero-downtime pepper rotation.
- [x] Generation: `clean_` + 44-char base58 body (uniform-random, rejection-sampling, no modulo bias) + 6-char CRC32 checksum, GitHub-style. Checksum rejects typos/truncations **before** the DB hit and sharpens the secret-scanning regex. Prefix configurable (`API_TOKEN_PREFIX`) — every clone needs its own.
- [x] Scopes — typed const `API_SCOPES = ["read:profile", "write:profile", "read:organizations"] as const`. Per-token subset, no global `*`, no `admin` scope (platform-admin surface is never token-reachable). **`read:uploads` dropped**: `modules/uploads/` exposes no listing route, persists no metadata table (the server is deliberately blind during upload), and storage is an opt-in docker profile — the scope would guard a route that can't exist without out-of-scope work. **Anti-escalation is structural, not a check**: token management lives outside `/api/v1`, so a token can never mint a token. Only remaining rule — an org scope requires the matching org permission at issuance.
- [x] `requireApiToken` middleware (alternative to `requireAuth`) — accepts `Authorization: Bearer clean_<…>`, verifies checksum, HMACs, compares, sets `c.var.user` + `c.var.tokenScopes`. Ban check included — a banned account cannot use its tokens.
- [x] **Public API surface is opt-in, route by route.** A PAT is *never* accepted by `requireAuth` — only a route that explicitly mounts `requireApiToken({ scopes })` is reachable by token. Every other route stays session-only, by construction rather than by config. **Why**: "authenticated" ≠ "public API" — a token that inherits the whole session surface turns every internal route (admin, billing mutations, impersonation) into a public endpoint the day it ships, and the blast radius of a leaked token becomes the entire app. The opt-in registry doubles as the source for any future API documentation: only token-reachable routes get documented.
- [x] `lastUsedAt` via time-bucket update (`WHERE last_used_at < now() - interval '15 min'`) — never one write per request (hot-row contention). Same bucket gives the `api_token.used` sampling for free.
- [x] `/settings/tokens` UI — create (name + scope picker + optional expiry), list (last-used timestamps), revoke. Created token shown ONCE in modal (reuse `<SecretRevealDialog>` from C.5), never persisted client-side.
- [x] Events: `api_token.created`, `api_token.revoked`, `api_token.used` (sampled, see above), all carrying `actorUserId` (rule #7).
- [x] Rate-limit **two axes**: per token (detects abuse of a legitimate/compromised key) and per IP (detects distributed attacks rotating tokens). One without the other is a blind spot.
- [x] GitHub Secret Scanning: the Partner Program requires a *public* service, so the boilerplate can't register — each clone does. Ship what makes it a 30-minute job: the configurable prefix, a ready `POST /api/token-scanning/github` revocation route verifying the **ECDSA P-256** signature (`GITHUB-PUBLIC-KEY-SIGNATURE` + `GITHUB-PUBLIC-KEY-IDENTIFIER` against `api.github.com/meta/public_keys/secret_scanning` — *not* the `X-Hub-Signature-256` HMAC used by regular webhooks), and the enrolment doc (see [`docs/INTEGRATIONS.md`](docs/INTEGRATIONS.md#6-github-secret-scanning-program)).

## In-app notification center — **Phase D.3** ✅ SHIPPED (Aug 2026)

**Why**: transactional emails are async; users miss them. An in-app inbox is the SaaS-default pattern (Linear, GitHub, Stripe). Persistent, mark-as-read, deep-linked.

**Design settled 2026-08-07** (full spec local, not versioned — `docs/superpowers/` is gitignored). SOTA baseline: Knock / Novu / Courier / SuprSend converge on six primitives (workflow engine, three-level preferences, batching + digest, critical bypass, throttling with dedup, inbox over feed). Two deliberate divergences: SSE instead of WebSocket, and a typed `Record<EventType, Config>` instead of a workflow DSL — the outbox already resolves fan-out, which is the only reason those platforms need a DSL at all.

- [x] **Fan-out = `NotificationFanoutSubscriber implements OutboxSubscriber`**, in the dispatch TX beside `AuditEventSubscriber` / `WebhookFanoutSubscriber` — **not** the `onEvent(...)` post-commit handler this spec originally suggested. **Why**: `onEvent` is best-effort and isolated, so a lost notification fails silently; and batching needs a transactional write (two concurrent events on one batch key without a lock produce two batches). Constraint: one `INSERT ... SELECT` joining members × preferences, never N inserts in a loop.
- [x] **Recipients resolved by capability, never by role tuple.** `type Audience = "self" | "actor" | "org:all" | { can: OrgPermissions }`. **Why**: `audience: "org:admins"` is exactly the hardcoded tuple org-scoping rule #6 forbids — it duplicates a decision owned by `@packages/access-control` and drifts the moment a role is added. Costs nothing at runtime: roles are static code, so `ORG_ROLES.filter(r => authorizeRole(r, perms))` resolves once at boot, leaving `WHERE member.role = ANY($1)`. **Trap**: `billing:["manage"]` is owner-only (`access-control/src/index.ts:33`) — a notification asks *who needs to know*, not *who may act*, so `read` is almost always the right level.
- [x] **`notification-map.ts`** — third projection of the catalog after `visibility-map` (webhooks) and `retention-map` (purge). Absent event = no notification (the default: most of the 67 events are audit-only). `forced: true` short-circuits preferences *and* batching, before either is evaluated (the SOTA critical bypass).
- [x] **Batching splits per channel.** In-app writes the row immediately and groups on read by `groupKey` (Linear's "X and 3 others"); email batches on write via `emailPendingAt` / `emailSentAt` columns. **Why no `notification_batch` table**: SaaS platforms need one because they don't own their customers' storage. We do — so the batch stays a query instead of state that can desync. Frequency preference (`immediate` / `hourly` / `daily`) supplies the window, which makes the scheduled digest the same cron with a longer one.
- [x] **Throttling = partial unique index** `(userId, dedupKey) WHERE dedup_key IS NOT NULL`, with the window baked into the key (`<eventType>:<resourceId>:<hourBucket>`). Dedup happens at insert inside the TX, so it's concurrency-correct; a counter would need an extra lock for the same guarantee.
- [x] Tables: `notification(id, userId, organizationId?, category, eventType, groupKey, dedupKey?, payload, readAt, emailPendingAt, emailSentAt, createdAt)` + `notification_preference(scope 'user'|'org', scopeId, category, channel, enabled, frequency, locked, updatedAt)`. Partial index `ON notification (user_id) WHERE read_at IS NULL` for the unread count. **`organizationId` nullable is a documented exception to org-scoping rule #3** — a notification is user-scoped by nature (`user.password_changed` belongs to no org).
- [x] **Preference cascade**: org lock → user preference → org default → enabled, with `forced` bypassing all four. Org-level is the SOTA B2B differentiator (Knock) and near-free here. **Applied inside the fan-out `INSERT ... SELECT`** (`LEFT JOIN notification_preference` per channel), which is the only place it can be both correct and single-query. **This line was checked while the cascade was inert** — the fan-out never read the table, `forced` was never read anywhere, and `NotificationPreferenceService.resolve` had zero callers; branched 2026-08-16 and the dead service deleted, because two implementations of one cascade with only one wired in will diverge. The `org default` level (an unlocked org row applying when the user made no choice) is an addition over that service, which ignored unlocked org rows: without it the org defaults card would set values that never apply. **Verified against Postgres, not unit-tested** — `pnpm --filter api check:fanout` covers 8 cases; a mocked `tx` evaluates no `WHERE`, and the repo has no DB integration harness.
- [x] **SSE stream carries a signal, never data.** `GET /notifications/stream` (Hono `streamSSE`) + Postgres trigger `pg_notify('notification_created', user_id)`, mirroring `outbox-dispatcher.service.ts:104`. **Why signal-only**: a reconnect just fires `invalidateQueries`, which by definition catches up — killing `Last-Event-ID`, replay, and merge logic in one stroke, and degrading naturally to polling if the stream dies. **`NotificationStreamHub` holds one `LISTEN` connection per instance**, never one per client (that exhausts the pool at a few hundred connected users); multi-instance works broker-free since `pg_notify` broadcasts to every listener. Heartbeat 25 s (Caddy timeouts). Client uses `fetch` + `ReadableStream`, **not `EventSource`** — it can't carry an `Authorization` header, which would break F.1's Capacitor bearer.
- [x] Front: `<NotificationBell />` in `app-shell`, `/settings/notifications` in `settingsLayout`; org defaults as a card inside `/settings/organization` (a route under `orgScopeLayout` would collide — it flattens children under `settings/`). Polling survives only as fallback: `refetchInterval: streamConnected ? false : 30_000`, plus `refetchIntervalInBackground: false` so a forgotten tab whose stream died stops polling. **Promotes `auth-broadcast.ts` into `createBroadcastChannel<T>(name)`** — 2nd occurrence triggers rule #2. **Everything cross-cutting lives in `apps/app/src/shared/notifications/`** (bell, item, preference matrix, grouping, labels, read-broadcast, stream hook), not in the feature: `shared/` may not import `features/`, and the matrix has two route-owning consumers (`features/notifications` + `features/organization`) which may not import each other. `features/notifications/` keeps only its route and page. Row labels reuse `EVENT_DESCRIPTIONS` rather than restating 21 strings; a fully-forced category renders disabled with its reason (`forcedLevelOf` in `@packages/events` — `security` is `all`, `billing` only `some`).
- [x] Crons on the existing `/internal/*` rail: `flush-notification-emails` (1 min — so `immediate` means "next tick"; true instant is the SSE's job) + `sweep-notifications` (**read rows only** — an unread notification outlives retention, same logic as D.5's `failed` rows).
- [x] **Notification creation emits no event.** D.3 consumes the catalog for fan-out — a `notification.created` event would loop with its own subscriber. Preference *mutations* (PUT /preferences, PUT /org-preferences) do emit audit events (`notification.preference.updated`, `notification.org_preference.updated`) because they are persistent state changes, not read projections. Catalog **67 / 28 public / 39 internal**.
- [x] Out of scope: native push (mobile / browser), generalized real-time bus, workflow DSL. **Also deferred**: frequency-driven digest windows — the `frequency` column and its selector ship and persist, but `flush-notification-emails` still treats every pending row alike, so `hourly` and `daily` currently behave as `immediate`. Honouring them is a cron change, not a schema change.
- [x] **Resend Broadcasts/Audiences rejected**: marketing one-to-many, orthogonal to event-driven one-to-one. Topics (Resend-side email preferences) also rejected — it would hand a product decision to the vendor and covers only one channel, when D.3 exists precisely to arbitrate *between* channels. Revisit Broadcasts if a clone ever ships a newsletter.

**New known debt found during closeout review**: the sweep routes and the cron client have no explicit timeout — `internalLayers` sets none, `Bun.serve` has no `idleTimeout`, `signedInternalFetch` issues a bare `fetch` with no `AbortSignal` — and doubling the sweep passes brings that closer to mattering. - [x] **The internal sweep rail is bounded — in time, and against itself.** Three nested deadlines (`SWEEP_DEADLINE_MS` 90 s < `SERVER_IDLE_TIMEOUT_SECONDS` 120 s < `INTERNAL_FETCH_TIMEOUT_MS` 150 s), with env parsing refusing a configuration that inverts them, plus a time-boxed lease in `sweep_lock` making each label single-flight. **Timeouts alone were never enough**: bounding a run does not stop the next tick from starting a second one, and two concurrent sweeps just split the `SKIP LOCKED` rows at double the pool cost — the lease is what actually removes the overlap, and it expires on its own so a crashed run does not wedge the label the way a pooled advisory lock would. The lease is fenced by an owner token (not just the label), because the deadline is only checked between batches — a run can outlive its own TTL, and without the token its late `release()` could steal back a lease a legitimate successor had already acquired. **Two live bugs found by measuring rather than reading the docs**: `Bun.serve` defaults `idleTimeout` to 10 s *and applies it while the handler runs*, so (a) every sweep past 10 s had its socket closed under it while the work continued server-side, and (b) `GET /notifications/stream`, whose heartbeat is 25 s, was being dropped and reconnected every 10 s in production. A third was found by reading: `sweep-notifications` was mounted but missing from the bundled cron, so read notifications were never purged — the cron now calls it. Sweeps out of budget answer `truncated: true` (derived per-pass from a `stopReasons` map — `exhausted` / `budget` / `batch-cap` / `batch-error`) and resume next tick; `stopReasons` keeps a recurring `batch-error` from hiding behind that, since one is a healthy backlog and the other is data that will fail identically forever, and the bundled cron exits non-zero on it. `rgpd-sweep` got the same budget between account wipes (never inside one — a half-erased account is the one Art. 17 outcome that must not happen) but deliberately no lease and no `SKIP LOCKED` on selection, so two overlapping runs can select the same account; the anonymizing update is guarded by `deletedAt IS NULL`, which is what makes the wipe itself idempotent and lets the losing run short-circuit before emitting `USER_DELETED` again. Its `processed` field now reports accounts actually attempted rather than the batch size, so a truncated run's response matches what it really did.

## Back ↔ front surface parity — **Phase H.1**

**Why**: a boilerplate is judged on what the cloner can *do*, not on what the API can serve. A backend capability with no UI is invisible — the cloner re-implements it, or never learns it exists. A UI with no backend is a dead button. Both read as "unfinished" to someone who just cloned. This audit runs **last** because it audits the finished surface: doing it before E.1b would only mean translating screens twice.

**Scope**: every HTTP route in `apps/api` (Hono RPC surface, `authClient` plugin surface, `/api/v1`, `/internal/*`) mapped to its front consumer, and every front call mapped back to a live route. The deliverable is a checked-in map, not a one-off grep: a route with no consumer must be *declared* UI-less (infra probe, cron, public API, IdP/webhook receiver) or it is a gap.

- [ ] **The map itself** — a table in `docs/FEATURES.md` (or its own `docs/SURFACE.md`): route → consumer, or route → documented reason for having none. Kept honest by a check that fails when a route appears in neither column, so the map can't rot the way a hand-written inventory does.
- [ ] **Known gaps found in the first pass** (2026-08-31):
  - `PUT /admin/users/:id/role` (`apps/api/src/modules/admin/routes.ts:80`) has no front mutation — the role is rendered read-only at `apps/app/src/features/admin-users/admin-user-detail.route.tsx:136`. A platform admin can't do from the UI what the API already audits and permits.
  - `POST /uploads/download` and `DELETE /uploads` (`apps/api/src/modules/uploads/routes.ts:32,42`) have zero consumers. The concrete consequence: replacing an avatar never deletes the old object (`upload-avatar.tsx:35-39` just re-points `authClient.updateUser({ image })`), so every clone leaks orphaned objects into its bucket forever. Either wire the delete into the replace flow, or delete the routes.
- [ ] **Declared UI-less, verified as intentional**: health probes, `/internal/*` sweeps + `build-info`, `/api/v1/*` (token-authed third parties), `/api/auth/scim/*`, `POST /api/token-scanning/github`, and the `quotas` module (no HTTP surface at all).
- [ ] **The inverse direction** — no front call to a route that doesn't exist, no disabled control or TODO standing in for a missing endpoint. First pass found none beyond the read-only role badge above.
- [ ] **Behavioural parity, not just route parity** — for each capability the back enforces (ownership scoping, `denyImpersonated`, quota and entitlement gates, rate-limit rejections, policy gates), the front has the matching affordance: the action is hidden or disabled where it would be refused, and the refusal renders as a localized message rather than a raw 4xx. A gate the front doesn't know about is a button that fails in the user's face.

## Cross-cutting rules

1. **No DDD for these integrations** — `modules/<context>/infrastructure/services/*` on the api side, `features/<x>/hooks/*` + `shared/api/` on the app side. If a concept becomes domain (e.g. a `Subscription` with its own rules), promote it into `modules/<context>/domain/` then.
2. **Env validated by zod** in `apps/api/common/env.ts` (api side, pending migration to `apps/api/src/shared/env.ts`) and `apps/app/src/shared/env.ts` (app side).
3. **Webhooks**: live in the owning module's `routes.ts` (`modules/<context>/routes.ts` exposes `POST /webhooks/<provider>`), mandatory signature verification before any processing.
4. **Secrets**: never committed, `.env.local` (gitignored) + 1Password/Doppler in production.
