# test rules

The test kit every workspace builds on: port and unit-of-work doubles for `bun test` (`./bun`, `./bun/unit-of-work`, `./bun/instrumentation`), the real-database check harness (`./check-harness`, `./require-local-database`), the layering scan (`./source-scan`), the accessibility gate (`./a11y`) and the shared vitest config. Auto-loaded under `packages/test/`. These rules hold for every test file in the monorepo; a guide adds only what is specific to its workspace.

## Rules

1. **BDD style, one test file per service, use case, store or repository, DTO or route file, under `__tests__/` (a module not yet migrated still spells it `__TESTS__/`)** (a service groups one `describe` per method). Mock at port level and assert the `Result`/`Option` transitions. A port or unit-of-work double is `mockPort<T>()` or `mockUnitOfWork()`, never a hand-written object. **Why**: a double typed against the real port fails to compile the day the port gains a method, a hand-written one keeps passing.
2. **Substitute through the seam the code already has, before reaching for a module replacement.** A handler that takes its collaborators as arguments, a route factory that takes a `deps` object, a class that takes its repository in the constructor: pass a fake, and the substitution is scoped by construction, typed against the real port, and visible in the test's first ten lines. Replacing the module is the fallback for the cases with no seam (a module-level singleton like `db`, a third-party SDK, a lib imported directly). **Why**: injection cannot reach past the object under test, so it cannot be the reason another test's verdict changed, and the day a collaborator gains a method the compiler names every fake that must grow. Reference shape: `modules/api-token/src/__tests__/infra/adapters/github-key-verifier.adapter.test.ts`.
3. **Stand in for a module by spreading the real one; never hand-copy its surface.** `mock.module("@packages/events", () => ({ ...realEvents, EventTypes, SomePayload: stub }))`, and derive any map from the real catalog (`Object.values(EventTypes).map(...)`) rather than listing its keys. **Why**: a hand-kept copy is correct exactly once; every export added afterwards silently becomes `undefined` in that file, and an assertion on it compares `undefined` to `undefined`, green and meaningless.
4. **A test file must not be able to change how another test file behaves, and the harness, not discipline, guarantees it.** Replacing a module, patching a global or mutating a shared fixture is legitimate *inside* the file that does it; if the effect can outlive that file, the suite's verdict becomes a function of file order. So every runner gives each test file its own module registry and globals (`bun test --isolate`, which `--parallel` implies; vitest by default), and a canary pair fails the moment that stops being true (`apps/api/CLAUDE.md`, Testing). Inside a file, reset shared mutable state in `beforeEach`. **Why**: an order-dependent suite goes green on wrong code and red on right code, and once a team has seen either, no result from it is believed again. **Test before merging a test file**: run it alone, then run the suite in another order (`bun test --isolate --randomize --seed=<n>`); a verdict that moves is a harness bug, never a flake to retry.
5. **Never claim logic is covered when it lives in SQL and the test mocks the transaction.** A mocked `tx` never evaluates a `WHERE`, a `CASE` or a `JOIN`: a green suite around such a method proves only that a method was called. Either keep the decision in TypeScript so a unit test can reach it, or write an executable check against a real database on the harness of this package, wired to a `check:*` script AND a step in `.github/workflows/ci.yml` in the same change (`apps/api/scripts/check-fanout-preferences.ts` → `check:fanout` is the reference shape). **The CI step is not optional bookkeeping**: a check nothing runs proves nothing. **Corollary**: never assert on the SQL text a builder produced in a file that replaces the query builder; reading a string back out of a stand-in asserts on the stand-in, not on the query.
